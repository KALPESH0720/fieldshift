# Soil cards, weather snapshots, and farmer alerts

## Soil Health Cards

Manual/lab soil tests use `POST /api/v1/plots/{plot_id}/soil-tests`; history is paginated at `GET /api/v1/plots/{plot_id}/soil-tests`, and individual tests support authenticated read/update/delete at `/api/v1/soil-tests/{id}`. N/P/K values are non-negative and bounded, pH is 0–14, organic matter is 0–100 percent. Responses record tested date, nutrient units (`kg/ha` or `mg/kg`), organic-matter unit, source/provenance, confidence, review status, and card upload link. Only `status=approved` tests feed recommendations.

Image upload is a raw JPEG or PNG request body to `POST /api/v1/plots/{plot_id}/soil-card-uploads` with `Content-Type: image/jpeg` or `image/png`. The service enforces the configured byte limit, verifies file signatures, scans via ClamAV, then writes to a private S3-compatible bucket with server-side encryption. ACLs are never made public. Users get an owner-scoped 5-minute signed read URL; no raw object URL or storage key is returned. Uploads fail closed when scanning or private storage is unavailable. ClamAV findings are rejected. Production configuration validation requires both.

The upload creates an OCR job (`queued` → `processing` → `needs_review` or `failed`) and Celery performs extraction. Extracted values, per-field confidence, and raw provider metadata are retained in the job for traceability. The farmer reviews `/api/v1/soil-card-uploads/{id}` and submits corrected/confirmed values to `/review`. Values below `SOIL_CARD_OCR_CONFIDENCE_THRESHOLD` (default 0.80) must be explicitly corrected before approval. OCR never directly creates a measured soil record. The approved record references the upload and reviewer. OCR retries use `/retry`; duplicate image digests for the same plot return 409.

Photo bytes and raw OCR metadata are purged after `SOIL_CARD_RETENTION_DAYS` (default 30); reviewed soil measurements and provenance remain. The daily Celery retention task deletes the object and clears raw OCR metadata. If an object deletion fails, the job remains eligible for another purge pass. Bucket lifecycle should match or exceed the application deadline; production operations must monitor the purge task.

## Weather and sowing alerts

`GET /api/v1/weather/plots/{plot_id}/forecast` is owner-scoped and uses Open-Meteo only; IMD is not currently configured or queried. Coordinates come from the plot geometry centroid. Cache keys use provider version plus latitude/longitude rounded to three decimal places; Redis is the fast cache and persisted weather snapshots are the fallback/source of audit. `WEATHER_CACHE_SECONDS` controls cache lifetime and `WEATHER_FRESHNESS_SECONDS` bounds snapshot freshness. The response keeps the existing normalized `current` and `forecast` fields for clients, and adds `hourly`, `daily`, and `variable_units` from Open-Meteo. Hourly values cover temperature, humidity, dew point, apparent temperature, precipitation and probability, rain/showers/snow, weather code, pressure, cloud cover, evapotranspiration/ET₀, vapor pressure deficit, wind, and layered soil temperature/moisture. Daily values include min/max temperatures, UV, sunrise/sunset, sunshine/daylight, rain/showers/snow/precipitation totals and probability, wind maxima/direction, solar radiation, ET₀, humidity/dew point, vapor pressure deficit, and growing degree days. Forecast data is requested for seven days in UTC. Provider units are returned alongside each field group; the legacy normalized fields use mm, Celsius, and m/s. The response includes an attribution label and URL for clients to display. Open-Meteo's free API is non-commercial and is subject to per-IP rate limits; commercial deployments must use an appropriate plan. See [Open-Meteo API documentation](https://open-meteo.com/en/docs) and [terms](https://open-meteo.com/en/terms).

Farmer settings are read/written at `GET/PUT /api/v1/weather/preferences`. Weather alerts, reminders, SMS, and WhatsApp default off. Preferences include quiet-hour window, IANA timezone, preferred language, and crops the farmer plans to grow. Forecast ingestion stores a snapshot for located, active plots. A sowing-window alert is generated only when the farmer opted in, selected a planned crop, the plot has an explicit district, an active crop rule is effective in that district and approved with `sowing_alert_enabled=true`, and the provider's crop-specific `sowing_window_days_remaining_by_crop` value is at or below that rule's `sowing_alert_threshold_days`. That crop/district threshold is reviewed with the rest of the rule by two agronomists; no global agronomic threshold is inferred. A deterministic per-plot/crop/rule/year dedupe key prevents hourly duplicates.

Alerts are listed at `GET /api/v1/weather/alerts`. The reminder dispatcher respects opt-outs, per-channel preference and quiet hours, and uses the farmer's language (English, Hindi, Kannada; other languages fall back to English). Delivery receipts are kept per channel. Failed channels retry with exponential backoff while successful channels are not sent again. Alerts move to `dead_letter` after `ALERT_MAX_ATTEMPTS`; the owner can replay an alert using `POST /api/v1/weather/alerts/{id}/replay`. Provider failure type, retry schedule, receipts, and dead-letter state are visible in the alert response. Operators should monitor the Celery queue and dead letters.

## Provider verification

Run the contract tests with `python -m pytest tests/unit/test_integrations.py tests/unit/test_weather_contract.py tests/unit/test_worker_tasks.py`. Open-Meteo forecast requests do not require credentials. The smoke script can verify the live forecast without messaging; to send one explicit test message, set `STAGING_SMOKE_PHONE` to a controlled test recipient and add `--send-test-message --channel sms` (or `whatsapp`). Output omits target numbers, secrets, response bodies, and forecast payloads. Open-Meteo requires product attribution and the current free API terms limit use to non-commercial projects; confirm the appropriate plan before commercial operation.
